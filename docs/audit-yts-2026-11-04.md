# Audit sistem YTS — 4–5 November 2026

Fokus: pengelolaan jamaah, dakwah, donasi, wakaf, kajian dan event Yayasan Tarbiyah Sunnah. Sekolah formal dikecualikan sesuai konfirmasi pengguna.

## Kesimpulan

Aplikasi sudah memiliki fondasi CRM jamaah dan operasional kajian yang luas. Sistem belum dapat disebut sebagai aplikasi event organizer lengkap: rundown, anggaran kegiatan, vendor, penjadwalan panitia, refund dan daftar tunggu belum ditemukan sebagai modul khusus pada kode dan skema yang diperiksa.

Audit ini mencakup rute aplikasi, matriks akses 10 peran, komponen halaman, pemanggilan API, skema, dan pengujian otomatis. Migrasi database, aktivasi 10 akun peran, serta perbaikan autentikasi, navigasi, privasi, tugas dan ekspor sudah diterapkan. Revamp dashboard admin dan perbaikan broadcast diterbitkan melalui PR #27 pada 5 November 2026. Bukti penerapan dan batas verifikasi terkini tercatat di `rollout-yts-2026-11-04.md`; kondisi pada tabel audit awal perlu dibaca bersama pembaruan di bagian akhir laporan ini.

## Alur yang saling terhubung

1. **Jamaah dan event:** pengurus membuat event → portal menerima pendaftaran → profil jamaah dan peserta tersimpan → tiket/QR → presensi → histori jamaah dan rekap kegiatan.
2. **Layanan jamaah:** profil/pertanyaan masuk → interaksi tercatat → tugas tindak lanjut → PIC memperbarui status → histori pada profil dan dashboard.
3. **Donasi:** konfirmasi portal/pencatatan petugas → transaksi belum diverifikasi → Finance memeriksa bukti/mutasi → status verifikasi → laporan dan email tanda terima.
4. **Wakaf:** permohonan → profil waqif → kasus dan tahapan → tugas/dokumen → perkembangan dan laporan.
5. **Komunikasi:** peserta atau segmen → kampanye/pengingat → provider email atau draf WhatsApp → hasil dan pencatatan interaksi. Draf WhatsApp membuka aplikasi WhatsApp; ini belum merupakan pengiriman otomatis melalui API WhatsApp.
6. **Konfigurasi:** administrator menyimpan identitas/rekening → portal menampilkan rekening tersebut → email konfirmasi memakai rekening dari sumber yang sama.

Relasi kode dan pengujian tidak menggantikan uji menyeluruh pada database, provider dan perangkat pengguna.

## Penerapan pada staging

Jangan menerapkan frontend autentikasi baru ke database lama tanpa migrasi dan provisioning berikut.

1. Pilih branch staging terisolasi. Set `DATABASE_URL` untuk aplikasi dan `DATABASE_URL_DIRECT` untuk migrasi ke branch yang sama. Gunakan `AUTH_SECRET` server acak, minimal 32 karakter di produksi.
2. Jalankan `npm run db:migrate:access`. Script menerapkan SQL tambahan `drizzle/0012_staff_credentials.sql`, yang membuat `app_user_credentials` dan `foundation_settings`. Script ini khusus migrasi tambahan karena jurnal migrasi lama belum mencakup seluruh SQL manual terdahulu.
3. Pastikan akun administrator aktif dan memiliki peran `crm_admin`. Set `INITIAL_ADMIN_EMAIL` dan `INITIAL_ADMIN_PASSWORD` minimal 12 karakter pada lingkungan lokal/server yang aman, lalu jalankan `npm run auth:bootstrap`. Kata sandi tidak ditulis ke kode atau output. Hapus variabel bootstrap setelah selesai.
4. Masuk sebagai admin. Gunakan pengaturan pengguna untuk mengatur kata sandi akun staf lama atau membuat akun baru. Akun tanpa hash belum dapat login. Mengganti password atau logout mengakhiri seluruh sesi lama akun tersebut.
5. Isi identitas dan rekening yayasan yang benar di Pengaturan, kemudian simpan ke server. Tidak ada nomor rekening contoh yang otomatis dipercaya sebagai rekening resmi.
6. Jalankan uji penerimaan di bawah sebelum menggunakan versi baru untuk operasional.

Tidak ada migrasi, bootstrap, perubahan kredensial, pengiriman email kepada pengguna, atau publikasi produksi yang dilakukan dalam pekerjaan audit ini.

### Data lama dan batas operasional

Produksi memiliki 6 event; roster terbesar 2.065 peserta. Ada 137 pendaftaran pada event berbayar dengan status lama `free`. Status itu belum cukup untuk menyimpulkan pembayaran atau pembebasan biaya. UI memberi tanda **Perlu ditinjau**, dan penambahan check-in memerlukan keputusan verifikasi; catatan pembayaran, nominal dan kehadiran lama tidak diganti otomatis. Tiga flag pendaftaran lama masih bernilai buka setelah jadwal lewat; daftar dan tombol pendaftaran kini mengikuti batas jadwal efektif tanpa mengganti status historis otomatis.

Modul sudah mencakup operasional kajian/daurah dan bazar. Pengembangan EO berikutnya yang belum memiliki alur khusus: rundown per sesi, pembagian divisi/shift panitia per event, RAB dan realisasi biaya, vendor umum di luar tenant bazar, inventaris alat, refund/pembatalan peserta, serta daftar tunggu peserta umum dengan promosi otomatis. Waitlist tenant bazar sudah ada; keluarga masih berupa rombongan per event, bukan master keluarga lintas kegiatan. Pengiriman email nyata, izin/perangkat kamera lapangan, dan kebenaran rekening harus diuji oleh penanggung jawab dengan data operasional yang sah sebelum digunakan untuk acara berikutnya. Area donasi publik di luar Events masih memiliki nomor contoh pada implementasi lama dan perlu audit modul tersendiri.
